# PostgreSQL Transactions Under Load

Практический проект для изучения и проверки того, **как PostgreSQL ведёт себя при конкурентных изменениях данных и высокой нагрузке**.

На примере банковских переводов показано, как построить транзакции, которые сохраняют целостность балансов при одновременной работе нескольких клиентов, а также как масштабировать таблицу операций и обрабатывать ошибки конкуренции на уровне приложения.

## 🎯 Что вы получите из этого проекта

Проект можно использовать как **практический стенд для изучения транзакций PostgreSQL и конкурентного доступа к данным**.

Здесь можно посмотреть готовые реализации и на их основе разобраться:

* как защищать баланс от некорректных конкурентных изменений;
* чем отличаются `Read Committed`, `Repeatable Read` и `Serializable`;
* когда возникают `Deadlock` и `Serialization Failure`;
* как проектировать защиту от дедлоков;
* как реализовать оптимистическую блокировку через версию записи;
* как организовать повтор транзакции после временной ошибки;
* когда транзакцию лучше контролировать в PostgreSQL, а когда — в приложении;
* как вести аудит изменений через PostgreSQL triggers;
* как использовать партиционирование для большой таблицы транзакций;
* как сочетать PostgreSQL и Go при работе с конкурентными транзакциями.

Это не просто пример CRUD-приложения — это **лабораторный стенд для экспериментов с реальными проблемами высоконагруженных систем**.

## 🔥 Какие задачи помогает понять проект

### 1. Конкурентные переводы

Представим, что два запроса одновременно изменяют один и тот же счёт.

Обычный подход может привести к конфликту или потере изменения.

В проекте показаны разные способы решения этой задачи:

* блокировка строк;
* проверка версии записи;
* транзакции PostgreSQL;
* обработка ошибок сериализации.

Это позволяет сравнить подходы и понять, **какой механизм использовать при конкретном сценарии нагрузки**.

## 🔒 Оптимистическая блокировка

Для `accounts` используется поле `version`.

Условно операция изменения выглядит так:

```sql
UPDATE accounts
SET balance = balance - $1,
    version = version + 1
WHERE id = $2
  AND version = $3;
```

Если другая транзакция уже изменила запись, `UPDATE` не затронет строку.

Приложение может определить конфликт и повторить операцию.

### Практическая польза

Этот подход позволяет изучить, как уменьшить количество длительных блокировок и организовать конкурентное изменение данных через **optimistic locking**.

---

## 🔐 Защита от Deadlock

При переводе между двумя счетами легко получить ситуацию:

```text
Transaction A → account 1 → account 2
Transaction B → account 2 → account 1
```

Обе транзакции могут ждать друг друга.

В проекте используется единый порядок получения блокировок — идентификаторы счетов предварительно сортируются.

```text
min(account_id) → max(account_id)
```

Таким образом, все операции пытаются захватывать блокировки в одинаковом порядке.

### Что можно изучить

* почему возникают дедлоки;
* как порядок блокировок влияет на них;
* как проектировать операции, уменьшающие вероятность `Deadlock`;
* почему даже при правильном проектировании приложение должно уметь обрабатывать `40P01`.

## 🔄 Retry после ошибок PostgreSQL

Конкурентные транзакции могут завершаться временными ошибками:

* `40001` — `serialization_failure`;
* `40P01` — `deadlock_detected`.

Go-приложение распознаёт такие ошибки и выполняет повторную попытку операции.

```text
Transaction
     │
     ├── success → done
     │
     └── 40001 / 40P01
              │
              ▼
           retry
              │
              ▼
          transaction
```

Это показывает практический паттерн, который используется в системах, где конкурентные транзакции являются нормальной частью работы.

## 📊 Уровни изоляции PostgreSQL

В проекте есть сценарии для экспериментов с:

### Read Committed

Базовый уровень изоляции PostgreSQL.

Позволяет увидеть поведение транзакций при параллельном изменении данных.

### Repeatable Read

Позволяет исследовать ситуацию, когда параллельные изменения приводят к ошибке сериализации.

### Serializable

Используется для сценариев, где требуется получить результат так, как будто транзакции выполнялись последовательно.

Например:

```text
Общая сумма всех счетов
        ↓
консистентный результат
```

### Зачем это нужно

Вместо теоретического описания уровней изоляции можно **запустить SQL-сценарии и увидеть поведение PostgreSQL на практике**.

## 🗃 Партиционирование таблицы transactions

Таблица операций разделена по времени:

```sql
PARTITION BY RANGE (created_at)
```

Например:

```text
transactions
├── transactions_2026_01
├── transactions_2026_02
├── transactions_2026_03
└── ...
```

Такой подход позволяет изучить:

* работу PostgreSQL partitioning;
* разделение больших объёмов данных;
* запросы по временным диапазонам;
* обслуживание исторических данных;
* удаление старых партиций без необходимости удалять миллионы строк из одной таблицы.

Для систем с большим количеством событий, платежей, логов или исторических записей этот подход особенно полезен.

## 📝 Аудит изменений

Изменения операций фиксируются автоматически через PostgreSQL trigger.

Это позволяет сохранять историю действий:

```text
операция
   ↓
изменение данных
   ↓
trigger
   ↓
audit log
```

Такой механизм можно использовать как основу для изучения:

* аудита финансовых операций;
* истории изменений;
* расследования проблем;
* технического журналирования важных действий.

## 🛡 Ограничения на уровне базы данных

Часть бизнес-правил реализована непосредственно в PostgreSQL.

Например:

```sql
CHECK (balance >= 0)
```

Это означает, что база данных сама не позволит записать отрицательный баланс.

Также обеспечивается уникальность комбинации:

```text
клиент + валюта
```

### Почему это важно

Критические ограничения не должны полностью зависеть от кода приложения.

Даже если другой сервис или SQL-запрос попытается записать некорректное значение, PostgreSQL сможет отклонить такую операцию.

## 🐹 Go + PostgreSQL

Go-приложение использует `pgx/v5` для работы с PostgreSQL.

Показан вариант, когда транзакция управляется непосредственно приложением:

```text
Go application
      │
      ▼
BEGIN
      │
      ├── operation
      ├── operation
      └── operation
      │
      ▼
COMMIT
```

Это позволяет посмотреть, как согласовать:

* транзакции PostgreSQL;
* хранимые процедуры;
* ошибки сериализации;
* retry;
* бизнес-логику приложения.
