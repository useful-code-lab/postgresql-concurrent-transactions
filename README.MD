🏦 PostgreSQL Banking System (High-Load & Fault-Tolerant)
Профессиональная реализация ядра банковской системы на базе PostgreSQL и Golang. Проект демонстрирует решение критических проблем конкурентного доступа, масштабирования данных и обеспечения целостности баланса.
🚀 Основные возможности (Key Features)🛠 Архитектура и Масштабируемость

* Партиционирование транзакций (Table Partitioning):
* Таблица transactions переведена на схему PARTITION BY RANGE (created_at).
   * Данные автоматически распределяются по ежемесячным физическим партициям (например, transactions_2026_03).
   * Использование Default Partition для предотвращения ошибок при выходе за границы диапазонов.
   * Результат: Мгновенный поиск по датам и возможность удаления старых архивов без нагрузки на БД.
* Оптимистичная блокировка (Optimistic Locking):
* Реализована версия перевода (v5) через проверку колонки version в таблице accounts.
   * Использование оператора GET DIAGNOSTICS для контроля ROW_COUNT в процедурах.
   * Результат: Высокая пропускная способность системы (High Throughput) за счет отказа от "тяжелых" блокировок строк.

🛡 Безопасность и Контроль транзакций

* Защита от дедлоков (Deadlock Prevention):
* Алгоритм принудительной сортировки UUID идентификаторов перед выполнением FOR UPDATE.
   * Гарантирует, что встречные транзакции всегда блокируют счета в одинаковом порядке (от меньшего ID к большему).
* Аудит и логирование:
* Внедрена автоматическая система логов через триггерную функцию audit_trigger_func.
   * Каждое изменение баланса фиксируется в таблице аудита с меткой времени.
* Бизнес-ограничения (Constraints):
* Строгий запрет отрицательного баланса (CHECK balance >= 0).
   * Уникальность пары "Клиент + Валюта" (индекс и ограничение на уровне таблицы).

⚙️ Прикладной уровень (Golang CLI)

* Retry-механизм: Реализован цикл автоматических повторов (до 5 попыток) при возникновении ошибок:
* 40001 (Serialization Failure) — конфликт в Repeatable Read.
   * 40P01 (Deadlock Detected) — обнаружение взаимной блокировки.
* External Transaction Management: Перенос управления транзакционным контекстом (BEGIN/COMMIT/ROLLBACK) на сторону приложения через pgx/v5.BeginFunc.

📊 Исследование уровней изоляции
В проекте реализованы SQL-сценарии для тестирования поведения БД под нагрузкой:

   1. Read Committed: Демонстрация базовой изоляции и защиты от "грязного" чтения.
   2. Repeatable Read: Отработка ошибок сериализации при параллельном изменении одних и тех же строк.
   3. Serializable: Пример построения абсолютно консистентных отчетов (например, общая сумма всех средств в банке) в условиях параллельных транзакций.

.
├── cmd/                # Исполняемые файлы Go (CLI интерфейс для переводов)
├── migrations/         # DDL (Таблицы, Партиции, Индексы, Ограничения)
├── procedures/         # Хранимые процедуры (v1 - v5: от простых к оптимистичным)
├── functions/          # Триггеры и логика аудита
├── scripts/            # Seed-данные для наполнения базы
├── tests/              # SQL-сценарии тестирования уровней изоляции
└── docker-compose.yaml # Окружение (PostgreSQL 15+)
